本システムは、Go 言語と SQLite3 組み込みデータベースをベースに構築された、軽量・高性能・依存関係ゼロの最新 POS（販売時点情報管理）および在庫管理システムです。従来の重量級 Web フレームワークや複雑なフロントエンドのビルドツールチェーンを排除し、クラシックなモノリシック階層アーキテクチャと純粋な DOM/RESTful API インタラクションモデルを採用しています。小売店や特産品店における、量り売り、多次元の前払い追跡、未価格設定商品のゼロ価格保留、フェイルセーフな注文変更などの複雑なビジネスシナリオの下での、高い信頼性と計算の正確性に焦点を当てています。

## 1. システムの全体アーキテクチャと設計思想

ソフトウェアエンジニアリングの観点から、本システムは「ミニマリズム」と「高凝集・低結合」の原則を貫き、究極の実行効率とメンテナンス負担ゼロを追求しています。

1. **依存関係のないバックエンド (Dependency-Free Backend)**: バックエンドは Go 1.20+ 標準ライブラリの `net/http` パッケージのみを使用して純粋な RESTful API を構築しており、サードパーティの HTTP ルーティングフレームワーク（Gin、Echo など）を一切導入していません。これにより、追加のフレームワークのオーバーヘッドや依存関係の競合を回避し、高い実行効率と極小のコンパイルサイズを確保しています。
2. **Pure Go 駆動の組み込みデータベース (Pure Go SQLite3)**: データ永続化層には `modernc.org/sqlite` ドライバを採用しています。このドライバは C99-to-Go 変換技術に基づいており、Go が SQLite3 データベースを操作する際に CGO (C-Go Interoperability) を有効にする必要が一切ありません。これにより、CGO コンパイル時の GCC/Clang への依存を完全に排除し、あらゆる開発環境でシームレスなクロスプラットフォームコンパイル（例：macOS 上で Windows ネイティブの静的バイナリをワンクリックでコンパイル）を可能にしています。
3. **ゼロビルドのフロントエンド (Zero-Build Frontend)**: フロントエンドUIは Vanilla JavaScript、ネイティブの CSS Variables、HTML5 のみで構築されており、Node.js、Webpack、Vite、npm などの複雑なコンパイルやパッケージングプロセスを排除しています。システムを実行するための静的ファイルを用意するだけでよく、運用や二次カスタマイズのハードルを大幅に下げています。

## 2. ソフトウェアの階層アーキテクチャとコード構成

システムのコードは、古典的な階層アーキテクチャ (Layered Architecture) に厳密に従っており、ソフトウェアエンジニアリングの観点から関心の分離 (Separation of Concerns) を実現しています。これにより、コアビジネスロジック層が外部のインターフェースプロトコルやストレージメディアの変更から影響を受けないようにしています。

```
+-----------------------------------------------------------------------+
|                     HTTP インターフェース層 (Handler Layer)               |
|   OrderHandler   |   ProductHandler   |   ReportHandler  |   System   |
+-----------------------------------------------------------------------+
                                   | (インターフェース呼び出し / DTO 伝達)
                                   v
+-----------------------------------------------------------------------+
|                         ビジネスロジック層 (Service Layer)               |
|   CheckoutService   |   InventoryService   |   ReportService          |
|  [逆ロードアルゴリズム] | [受取数不足防止チェック] |    [ゼロ価格自動同期]      |
+-----------------------------------------------------------------------+
                                   | (依存性の注入 / インターフェース分離)
                                   v
+-----------------------------------------------------------------------+
|                       データアクセス層 (Repository Layer)                |
|   OrderRepo      |   ProductRepo      |   ReportRepo                  |
+-----------------------------------------------------------------------+
                                   | (ネイティブ SQL / トランザクション Tx)
                                   v
+-----------------------------------------------------------------------+
|                    インフラストラクチャ層 (Infrastructure Layer)          |
|   SQLite3 Database Engine    |    Windows RAW winspool.drv Printer    |
+-----------------------------------------------------------------------+
```

### 2.1 インターフェース層 (Handler Layer)
`internal/handler` ディレクトリに配置され、HTTP リクエストの受信、パラメータの解析、データの検証、および JSON レスポンスのフォーマットを担当します。各ハンドラはデータベースを直接操作せず、構造体のメンバを通じて依存するビジネス Logic/Service インターフェースを参照します。

### 2.2 ビジネスロジック層 (Service Layer)
`internal/service` ディレクトリに配置され、システムのコアとなるビジネスロジックとセキュリティ検証を担います。
* **依存性の注入 (Dependency Injection)**: システムの起動エントリーポイント `main.go` にて、各 Service に具体的な Repository の実装インスタンスを注入します。この疎結合設計により、将来的なユニットテスト（モック）やストレージエンジンの切り替え時に、ビジネスロジックのコードを変更する必要がなくなります。
* **並行処理と非同期の分離 (Concurrency & Async Decoupling)**: ハードウェアの IO 操作（サーマルプリンタでのレシート印刷など）に対しては、Service 層で Go コルーチン (`go printAsync`) を用いて非同期に処理を分離します。ユーザーの基盤ハードウェアが待機中や応答遅延状態であっても、メイン処理スレッドは完全に非同期かつノンブロッキングで動作し、即座に HTTP ステータス結果を返してデータベースのトランザクションを完了させることで、フロントエンドPOSの高い応答性を保証します。

### 2.3 データアクセス層 (Repository Layer)
`internal/repository` ディレクトリに配置され、すべての SQL ステートメントの構築、実行、および結果セットのマッピングを担当します。この層は、上位層から基盤となる SQLite ステートメントの複雑さを隠蔽し、テーブル結合の深いクエリ、ページネーション、複数フィールドのキーワード検索、および複雑な集計統計の実行を担当します。

### 2.4 インフラストラクチャ層 (Infrastructure Layer)
`pkg/printer` ディレクトリに配置され、オペレーティングシステムの周辺機器やリソースのスケジューリングを担当します。
* **プリンタドライバの抽象化インターフェース**: グローバルな標準インターフェース `Printer` とそのコアメソッド `PrintTicket(content string) error` を宣言します。
* **Windows API の深いカプセル化**: Windows 環境で一般的な POS-58 サーマルプリンタに対し、重いグラフィカル描画ドライバは呼び出しません。代わりに、Go の `syscall` と `unsafe.Pointer` を使用して、Windows のコア動的リンクライブラリ `winspool.drv` 内の `OpenPrinterW`、`StartDocPrinterW`、`WritePrinter` などのコア API を直接呼び出します。Go 内部の標準 UTF-8 文字列をプリンタがネイティブにサポートする GBK エンコーディングに変換した後、RAW モードでプリンタポートに直接バイトストリームと ESC/POS のハードウェア用紙カットコマンドを送信し、低遅延と高いハードウェア互換性を実現しています。

## 3. コアアルゴリズムと高度なビジネスメカニズム

実店舗経営におけるデータの一貫性、人的エラーの防止、リアルタイムな価格反映などの課題を解決するため、システムはいくつかの高度なコアアルゴリズムを実装しています。

### 3.1 予約注文の「リバースローディング」と「フェイルセーフチェック」アルゴリズム
POS 業務では、保留中（Pending）の予約注文に対して、ユーザーが支払い前に商品の数量、単価、または前受金を何度も変更する可能性があります。そのため、システムは「エラーを防ぐためのリバースローディング」アルゴリズムを設計しました。

1. **メモリ・スナップショットと逆マッピング**: ユーザーが過去の予約注文の変更をリクエストすると、システムはデータベースの `order_items` テーブルから該当注文のすべての行を抽出し、メモリ上の標準的なショッピングカートオブジェクト (`cart`) として復元・フォーマットします。同時に、グローバル状態をその注文の「編集ロック状態」としてマークします。
2. **安全在庫の双方向補正メカニズム**:
   * 注文変更を送信する際、システムは新しいカート内の各商品の数量と元の注文内の対応する商品の数量の差分 (`delta = new_qty - old_qty`) をリアルタイムで比較します。
   * `delta > 0`（追加注文）の場合、システムは排他的な在庫チェックを呼び出し、メイン在庫が十分であるか検証します。十分であればメインテーブルから `delta` 分の在庫を差し引き、不足していれば即座にトランザクションをブロックし、警告を返します。
   * `delta < 0`（注文減）の場合、システムは自動的に差額を解放し、メイン商品データベースの実際の在庫に戻します。
3. **受取数量の矛盾防止アルゴリズム (Pick-up Safety Check)**: 注文変更や部分返金のロジックにおいて、システムはすべての商品行に対して厳密に以下の公式で検証を行います。
   $$\text{ValidQty} \ge (\text{QtyPicked} - \text{QtyRefunded})$$
   レジ係が注文数を変更または返金しようとした結果、注文数が「すでに顧客が受け取った（かつまだ返金されていない）数量」を下回る場合、ビジネスサービスは直ちにセキュリティ例外をトリガーします。この検証により、「商品はすでに持ち帰られているのに、請求書が削除または返金される」という資金的リスクを根本から排除します。

### 3.2 一時商品の「ゼロ価格保留」と「価格自動同期」アルゴリズム
生鮮食品や新規入荷バッチなど、バックエンドでの在庫価格設定が完了していないが、フロントエンドで至急販売を開始する必要があるシナリオ向けに、システムは価格の遅延決定と自動補正マッピングのメカニズムを設計しています。

1. **ゼロ価格のプレースホルダーとメモリマーキング**: フロントエンドがまだ価格設定されていない商品を一時的にカートに入力すること（仕入価格と現在の価格はデフォルトで 0 に初期化されます）を許可し、保留注文を生成して対応する在庫と顧客属性をロックします。
2. **入庫トリガーメカニズム**: バックエンド管理者が調達モジュール (`Procure`) でこの一時商品の仕入価格と現在価格を補充して保存すると、永続化が完了した後、システムの更新トランザクションがアクティブに在庫と価格の更新コマンドをディスパッチします。
3. **自動同期と連携補完アルゴリズム**: フロントエンドが更新信号を受信すると、メモリ上のカートと保留注文プールのマッチングトラバーサルを実行します。保留注文状態または現在のカート内にある商品で、ID が一致し、履歴価格が 0、かつ最新価格が 0 より大きいすべての商品に対して、システムは直ちにメモリ内で最新の単価と仕入価格を自動補完し、`calcMargin()` と合計の再計算・レンダリングをトリガーします。この同期プロセスは完全に自動化されており、混雑するレジで履歴注文を手動で探し出して価格を変更するという煩雑な作業を完全に排除します。

### 3.3 単品レベルの支払いと受取の追跡メカニズム (Item-Level Tracking)
「注文全体」に対して「支払い済み/未払い」の二元的な判定しか行わない一般的なレジシステムとは異なり、本システムはデータ構造レベルで、**独立したSKU商品ごと**に4つの細分化されたカウント追跡を導入しています。
* **`qty_ordered`**: 初期の注文総数
* **`qty_picked`**: すでに受け取った（消し込み済み）数量
* **`qty_paid`**: すでに前払い/決済された数量
* **`qty_refunded`**: すでに返品された数量

**受取・支払い漏れ防止アルゴリズム**: 顧客が保留注文に対して分割受取 (`Pickup`) を行う際、受取リスト内の特定の商品が過去の保留時に前払いとしてマークされていなかった場合、システムは `qty_picked += delta` の更新を実行すると同時に、自動的にその商品の `qty_paid` を受取数量以上の値に同期させます。この設計により、物理的に受取が発生した商品は、その属性において必然的に「決済済み」としてマークされることが論理の最下層で保証され、業務プロセスで発生しうる代金回収漏れのリスクを防ぎます。

### 3.4 アトミックなシステムクリア・リセットアルゴリズム (Atomic System Reset)
デプロイとデバッグの完了後に商業用の本稼働に切り替える際や、旧バージョンからの完全なリセットといったビジネス要件に適応するため、システムはアトミックなリセット API (`/api/system/reset`) を実装しています。
1. **排他トランザクションの開始**: `db.BeginTx` を実行して排他ロックを取得し、クリアプロセス中の外部からの同時書き込みを防ぎます。
2. **外部キーの逆順クリア**: リレーショナルデータベースの外部キー制約の順序に厳密に従い、以下を順次実行します。
   * `DELETE FROM order_items;`
   * `DELETE FROM orders;`
   * `DELETE FROM products;`
3. **自動インクリメント主キーのゼロリセット**: システムは SQLite の基礎システムテーブルに対して `DELETE FROM sqlite_sequence WHERE name IN ('products', 'orders', 'order_items');` を実行します。これにより、リセット後の新しい商品番号と販売注文番号が、必ず数字の `1` から正確に順番に増加することが保証されます。
4. **物理スペースの回収**: トランザクションが正常にコミットされると、基盤データベースは自動的に `VACUUM;` コマンドを実行します。このコマンドは SQLite 内部のページ構造を再編成し、削除されたレコードが占有していた物理ディスクセクタを解放して、データベースファイルのサイズを小さく保ち、クエリの効率を維持します。

## 4. データベース設計と ER モデル

システムの基盤となるコアな永続化構造は 3 つの主要テーブルでサポートされており、完全なインデックスと関連計算をサポートしています。

### 4.1 商品在庫テーブル (`products`)
* **`id`** (INTEGER PRIMARY KEY AUTOINCREMENT): システム内部の連番ID。
* **`barcode`** (TEXT UNIQUE): 商品のバーコード/電子はかりスキャンマーカー。データベースレベルで一意のインデックスを作成し、スキャン検索を高速化します。
* **`name`** (TEXT NOT NULL): 商品の標準名称。
* **`category`** (TEXT NOT NULL): 商品の所属カテゴリ。一括変更や集計をサポート。
* **`cost_price`** (REAL NOT NULL): 商品の仕入原価。リアルタイムの粗利益率と純利益の計算に使用されます。
* **`price`** (REAL NOT NULL): フロントエンドの小売価格。
* **`stock`** (INTEGER NOT NULL): 現在利用可能な物理在庫（注文に基づく自動増減および事前控除をサポート）。
* **`unit`** (TEXT NOT NULL): 商品の計量単位（例：個、kg、箱、グラム）。

### 4.2 注文メインテーブル (`orders`)
* **`id`** (INTEGER PRIMARY KEY AUTOINCREMENT): システムのグローバルな一意の注文連番。
* **`daily_seq`** (INTEGER NOT NULL): 日次のキュー（順番待ち）連番。システムは1日を周期としてゼロにリセットし自動で再計算するため、実際の店舗シーンに合った短い番号を提供します。
* **`customer_name`** (TEXT): 予約顧客名。
* **`phone`** (TEXT): 予約顧客の電話番号。フロントエンドで電話番号のプレフィックスに基づく高速なあいまい検索をサポートします。
* **`total_amount`** (REAL NOT NULL): この注文で注文された商品の請求総額。
* **`paid_amount`** (REAL NOT NULL): この注文で実際に前払い/決済された金額。
* **`status`** (TEXT NOT NULL): ステータス列挙: `Pending` (予約保留)、`Completed` (リアルタイム決済完了)、`Refunded` (全額返金済み)、`Partial` (部分返品/部分返金が発生)。
* **`created_at`** / **`updated_at`** (DATETIME): トランザクションの作成タイムスタンプと最終変更タイムスタンプ。

### 4.3 注文商品明細テーブル (`order_items`)
`orders` と `products` 間の多対多のマッピングキャリアとして機能すると同時に、履歴上の瞬間的な価格とスナップショットの追跡を保存するという重要な役割も担います。
* **`id`** (INTEGER PRIMARY KEY AUTOINCREMENT): 明細行ID。
* **`order_id`** (INTEGER NOT NULL, FOREIGN KEY -> orders.id): 関連するメインテーブルのID。
* **`product_id`** (INTEGER NOT NULL, FOREIGN KEY -> products.id): 関連する商品のID。
* **`product_name`** (TEXT NOT NULL): 注文スナップショット名（将来の商品名変更が過去のレシートに影響するのを防ぎます）。
* **`price`** (REAL NOT NULL) / **`cost_price`** (REAL NOT NULL): 注文確定瞬間の小売価格と仕入価格のスナップショット。
* **`qty_ordered`** / **`qty_picked`** / **`qty_paid`** / **`qty_refunded`** (REAL NOT NULL): 数量ステータス遷移の 4 つの要素。

## 5. コンパイル、クロスプラットフォームビルド、およびデプロイ仕様

本システムは外部の実行環境や C 言語コンパイラへの依存を排除しているため、Go ツールチェーンから直接、クロスプラットフォームのデプロイと静的バイナリの生成を実行できます。

### 5.1 ローカルでのコンパイルと実行
Go 1.20 以上の開発環境を準備した後、プロジェクトのルートディレクトリに移動して以下のコマンドを実行します。

```bash
# Go Modules の依存関係の同期と検証（主に modernc.org/sqlite Pure Go ドライバ）
go mod tidy

# 現在のオペレーティングシステム用の静的バイナリ実行ファイルをコンパイル
go build -o modern-pos main.go

# POS サーバーの起動
./modern-pos
```

プログラムを起動すると、サーバーはデフォルトでローカルネットワークインターフェースに安全にバインドし、`127.0.0.1:8080` をリッスンします（本番環境で誤って `0.0.0.0` にバインドして外部ネットワークに公開されるのを防ぎます）。任意の最新ブラウザを使用して `http://127.0.0.1:8080` にアクセスすると、ログインしてシステムを操作できます。本番環境のデプロイでは、明示的なネットワークアダプタの IP を指定し、ファイアウォールまたはセキュリティグループのルールと組み合わせてアクセスを厳密に制限することをお勧めします。

### 5.2 クロスコンパイルと CUI レスデプロイ (Windows POS ネイティブ対応)
大多数の実店舗で採用されている Windows オペレーション環境に適応するため、環境変数を使用し、コマンドプロンプトウィンドウを必要としない純粋なネイティブ Windows アプリケーションをワンクリックでクロスコンパイルできます。

```bash
# Linux / macOS 上で Windows X86-64 アーキテクチャ用プログラムをクロスコンパイル
# -ldflags="-s -w -H windowsgui" の役割:
#   -s -w : デバッグシンボルを削除し、コンパイル生成された EXE ファイルのサイズを大幅に圧縮
#   -H windowsgui : Windows 起動時の黒いコマンドプロンプトウィンドウを非表示にし、プログラムをサービスとしてバックグラウンドで静かに実行
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w -H windowsgui" -o modern-pos.exe main.go
```

生成された `modern-pos.exe` と `static` ディレクトリを同じフォルダに配置し、店舗のコンピュータ上でダブルクリックするだけで直接実行できます。ターゲットのホストに Go 環境、Node ランタイム、またはデータベースソフトウェアをインストールする必要は一切ありません。

### 5.3 データベースの高信頼性とバックアップ/復元戦略
システムの実行中、作業ディレクトリに `pos_data.db` ファイルが自動的に生成され、組み込みの SQLite3 物理ストレージメディアとして操作されます。
* **WAL 並行書き込み先行モード**: 初期化時に、システムは明示的に `PRAGMA journal_mode=WAL` (Write-Ahead Logging) と `PRAGMA busy_timeout=5000` (5 秒のビジー待機タイムアウト) を有効にします。これにより、高並行性のトランザクションとバッチレポートのクエリが同時に発生した場合でも、読み書きロックの競合を完全に解決し、`database is locked` 例外を排除します。
* **定期的なホットバックアップと整合性チェック**: デフォルトで 6 時間ごとに基盤となるアトミックなホットバックアップを自動実行する `BackupService` バックグラウンド定期タスクが組み込まれています。バックアップには SQLite のゼロブロッキングアトミックコマンド `VACUUM INTO` を使用してスナップショットを生成します。生成後すぐにスナップショットを開いて `PRAGMA integrity_check` による深い整合性チェックを実行し、エラーがないことを確認した後、自動的に `./backups` ディレクトリに保存し、30 日を超えた過去のスナップショットをクリーンアップします。検証でスナップショットの破損が発見された場合は、即座に安全に破棄され、アーカイブファイルが 100% 復元可能であることを保証します。
* **システム高リスク操作の認証と行数監査**: `/api/system/backup`、`/api/system/restore`、`/api/system/reset` などの高リスクな保守インターフェースには、`RequireAdmin` 権限検証ミドルウェア（タイミング攻撃を防ぐための `subtle.ConstantTimeCompare` 経由）を強制適用します。注文の控除および返品の基盤となる Repository の SQL 実行では、影響を受ける行数 (`RowsAffected`) を厳密に検証し、複数のユーザーによる並行処理下での在庫の過剰な引き落としや受取数量の逆転を防ぎます。

### 5.4 安定性保証、オブザーバビリティ（可観測性）、および CI/CD 仕様
* **完全なオブザーバビリティ監査 (Logging Middleware)**: システムは、すべての HTTP 呼び出しのマイクロ秒レベルの応答時間と実際のステータスコードをインターセプトして記録します。`/api/checkout`、`/api/refund`、`/api/inventory/*`、`/api/system/*` などの重要な決済および在庫管理パスに対しては、専用の `[Business Audit]`（ビジネス監査）ログを自動出力します。
* **自己修復と安全保護 (Panic Recovery & Server Timeouts)**: グローバルな `Recovery` ミドルウェアを通じて、処理されていないすべての実行時例外 (Panic) をインターセプトし、スタックトレースを保存します。局所的な障害が発生した場合、クライアントに安全で親切な HTTP 500 エラーを返し、メインプログラムのプロセスはクラッシュしないため、他のレジの営業継続を保証します。同時に、基盤となる `http.Server` に `ReadTimeout (15s)`、`WriteTimeout (30s)`、および `IdleTimeout (60s)` を厳格に設定し、スロー攻撃や長時間の接続ハンドルの枯渇を完全に防ぎます。
* **グレースフルシャットダウン (Graceful Shutdown)**: システムはバックグラウンドでオペレーティングシステムの停止シグナル (`SIGINT`/`SIGTERM`) をリッスンします。停止コマンドを受信すると、まず定期的なホットバックアップタスクを優雅に停止し、新しい書き込みがトリガーされるのを防ぎます。次に、`srv.Shutdown(ctx)` を通じて、現在アクティブなトランザクションとダウンロードのために 10 秒の完了準備時間を確保します。最後に、`sql.DB` ドライバを安全に閉じ、先行書き込みログが完全にディスクに書き込まれることを確認します。
* **継続的インテグレーションと自動クロスコンパイル (GitHub Actions CI/CD)**: プロジェクトには完全な `.github/workflows/ci.yml` 自動化パイプラインが構成されています。コミットまたは Pull Request ごとに環境が自動起動し、コード規約チェック、ユニットテスト、および並行性競合チェック (`go test -race ./...`) を実行します。自動ビルドマトリックスを通じて、リリースごとに Linux (amd64)、Windows (amd64 GUI 版)、および macOS (Intel amd64 と Apple Silicon arm64) 向けのネイティブ実行ファイルを同時にコンパイルし、Release としてアーカイブします。
